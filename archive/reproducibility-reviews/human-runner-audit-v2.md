# Adversarial audit of `human-runner`

Audit date: 2026-08-26

Scope:

- `/hpc/users/sunh14/.codex/skills/human-runner/SKILL.md`
- `agents/openai.yaml`
- all four files under `references/`

Controlling interpretation: minimize what a practitioner must understand. Reproducibility is the adoption boundary and evidence proxy, not an independent reason to add machinery. This audit does not propose a replacement skill.

## Verdict

The priority is now substantially correct. The skill consistently prefers existing practitioner-native facilities, keeps experiments free, makes templates and records conditional, and permits honest `unverified` claims instead of custom assurance machinery.

It is not yet airtight. Three findings are critical:

1. “retained output” conflates authored project changes with derived execution outputs;
2. a production run can cite an immutable revision without explicitly running from a state that matches it; and
3. a blocker is written as an alternative condition for calling the task complete.

The package also lacks the promised visible rule classification, contains a few adoption and sequencing gaps, and imposes some agent-process ceremony that conflicts with its own simplicity priority.

Severity:

- **Critical:** permits laundering, false completion, or a retained result that cannot be tied to the claimed production path.
- **Significant:** materially weakens the priority, evidence boundary, or practical adoption.
- **Minor:** ambiguity or friction with limited likely impact.

## Numbered findings

### HR-01 — Authored changes and derived outputs are conflated

**Severity:** Critical  
**Categories:** production-path loophole; contradiction; practical complexity

**Exact sentences**

> “Accept retained work only when it came from the simplest conventional production path…” — `SKILL.md:16`

> “Treat an experimental result, value, dependency, observation, environment effect, or artifact as adopted when … it is delivered…” — `SKILL.md:40`

> “Confirm that every retained output comes from a production execution…” — `references/evidence-tests.md:15`

**Loophole**

Source, configuration, and documentation are retained deliverables but normally originate as authored edits, not production executions. An agent can read the clauses two ways:

- force every authored edit through artificial regeneration machinery; or
- call a genuinely derived artifact “authored” and bypass regeneration.

Both violate the objective.

**Minimal fix**

Add one definition:

> Authored retained changes are promoted by a reviewable retained edit and the relevant ordinary check. Derived retained outputs are regenerated by the production path. Never relabel derived content as authored to avoid regeneration.

Change “every retained output” in the adoption test to “every retained derived output and every execution result cited as evidence.”

### HR-02 — The production workspace need not match the cited revision

**Severity:** Critical  
**Categories:** uncommitted production run; laundering

**Exact sentences**

> “an immutable identity for load-bearing source and configuration” — `SKILL.md:58`

> “Allow drafts to be tidied until a revision is cited…” — `SKILL.md:44`

**Loophole**

The skill requires an immutable identity but never directly says that the executing workspace must match it. An agent can run dirty load-bearing code while recording a clean revision. The clean-start reference test may detect this later, but it is loaded only before acceptance and is not a production-run precondition in the main skill.

**Minimal fix**

After `SKILL.md:58`, add:

> The execution state must match the cited revision and contain no unrecorded load-bearing difference. Unrelated user changes may remain only when the production operation cannot read them.

### HR-03 — A blocker can be called completion

**Severity:** Critical  
**Categories:** false status; contradiction

**Exact sentence**

> “Do not call setup, submission, a rerun, or the task complete until expected final outputs exist and pass the stated criterion, **or** a concrete blocker and unverified scope are documented.” — `SKILL.md:78`

**Loophole**

The disjunction makes a documented blocker sufficient to call the task complete.

**Minimal fix**

Replace with:

> Call the operation complete only when expected final outputs exist and pass the stated criterion. If blocked, stop and report the operation as blocked or incomplete, with the blocker and unverified scope.

### HR-04 — An experimental derived artifact can be relabeled as an acquired input

**Severity:** Critical  
**Categories:** experimental output carried into deliverable; adoption abuse

**Exact sentences**

> “Promote adopted knowledge through ordinary retained project artifacts, then regenerate the retained result…” — `SKILL.md:40`

> “Preserve stable origin, identity, access procedure, expected location, compatibility, and retention for acquired inputs…” — `SKILL.md:69`

**Loophole**

An agent can take an experimental derived file, declare it an “acquired input,” and make the production path consume it. The downstream result is regenerated, but the experimental intermediate was carried across the boundary.

**Minimal fix**

Add to `SKILL.md:69`:

> An experimental derived artifact cannot be promoted as an acquired input. Promote its producing operation, inputs, and parameters, then regenerate it. A genuinely human-curated primary input follows the curation rule below.

### HR-05 — Recording an experimental decision is optional

**Severity:** Significant  
**Categories:** chosen experimental result; softening

**Exact sentence**

> “If none exists, add one terse append-only entry **only when a practitioner needs it**…” — `SKILL.md:42`

**Loophole**

The agent may decide that a practitioner does not “need” the decision and omit a parameter, threshold, expected value, dependency choice, or why-not decision determined by experimentation.

**Minimal fix**

Replace the quoted qualifier with:

> If no durable practitioner-facing mechanism exists, add one terse entry whenever the experiment changes production behavior, fixes a parameter or criterion, selects among results, or excludes a plausible alternative a practitioner might revisit.

### HR-06 — Experimental influence can be denied unless it “fixes” a formal decision

**Severity:** Significant  
**Categories:** hidden adoption; honor surface

**Exact sentences**

> “When an experiment fixes a production decision…” — `SKILL.md:42`

> “Do not record experiments that shaped nothing.” — `SKILL.md:42`

**Loophole**

An experiment may reveal a bug cause, invalidate an approach, or shape implementation logic without “fixing” a named decision. The agent can call that ordinary reasoning and omit the load-bearing observation.

**Minimal fix**

Define “shapes a decision” to include changing implementation behavior, setting any production value or expectation, or excluding a plausible alternative. Keep uninfluential trials unrecorded.

### HR-07 — A mutated experimental environment can pass as “validated”

**Severity:** Significant  
**Categories:** experimental environment adoption

**Exact sentences**

> “environment requirements sufficient to rebuild **or validate** the production environment” — `SKILL.md:59`

> “Rebuild rather than adopt accidental experimental environment state.” — `SKILL.md:67`

**Loophole**

An agent can call the experimental state deliberate, perform a shallow version check, and claim it was validated rather than adopted.

**Minimal fix**

Add:

> Validation must establish the declared resolved identity and absence of unrecorded load-bearing modifications. If it cannot, rebuild.

### HR-08 — Persistent experimental shared state can leak into production

**Severity:** Significant  
**Categories:** effect-based adoption; experiment/production line

**Exact sentences**

> “Shared-system effects … need production records only when a retained output relies on them.” — `SKILL.md:38`

> “Unknown load-bearing dependencies count.” — `SKILL.md:36`

**Loophole**

An experiment can create cache, database, service, queue, or remote state that a later production run consumes. Because dependency completeness is honor-based, the agent can deny or overlook the reliance.

**Minimal fix**

Do not require experiment cleanup. Instead add to the production precondition:

> Identify or validate every load-bearing shared start state consumed by the production run. If experimental shared state may affect the result and cannot be distinguished, mark the result unverified and do not claim clean regeneration.

### HR-09 — Free shared-system experimentation conflicts with the intervention rules

**Severity:** Significant  
**Categories:** contradiction; two-way reading

**Exact sentences**

> “Shared-system effects … need production records only when a retained output relies on them.” — `SKILL.md:38`

> “Treat state-changing diagnosis as a production intervention…” — `SKILL.md:83`

> “Do not modify a shared production environment in place without a retained declaration.” — `SKILL.md:67`

**Loophole**

It is unclear whether an authorized experimental diagnostic that changes shared production state is free, a production intervention, or prohibited environment mutation.

**Minimal fix**

Add one precedence sentence:

> State-changing diagnosis or environment modification against real production state is an intervention regardless of whether its result is adopted; other authorized shared-system experiments remain free with respect to project recording.

This preserves the deliberate “experiments are free” design while removing the real-production-state ambiguity.

### HR-10 — “One” documented operation can create a wrapper solely to satisfy the skill

**Severity:** Significant  
**Categories:** complexity accretion; human-native failure

**Exact sentence**

> “one ordinary documented human operation” — `SKILL.md:61`

**Loophole**

A legitimate production path may contain two or three conventional commands. “One” invites an artificial wrapper or omission.

**Minimal fix**

Replace “one” with:

> the smallest set of ordinary documented human operations; never add a wrapper merely to collapse the set to one.

### HR-11 — A cited revision may be immutable but unavailable

**Severity:** Significant  
**Categories:** recreation gap; evidence retention

**Exact sentences**

> “From that point, keep the cited revision unchanged…” — `SKILL.md:44`

> “an immutable identity for load-bearing source…” — `SKILL.md:58`

**Loophole**

A local revision identifier can remain unchanged yet disappear or be inaccessible to the stranger.

**Minimal fix**

Require the cited revision’s stable locator, access, and retention for the lifetime of the evidence that cites it. Use existing version-history facilities; add no new storage mechanism.

### HR-12 — Existing decision mechanisms need not be durable or human-facing

**Severity:** Significant  
**Categories:** hidden session dependency; human-native form

**Exact sentence**

> “use the existing decision mechanism” — `SKILL.md:42`

**Loophole**

The existing mechanism could be chat, an agent-only file, an ephemeral ticket view, or a mutable note without retained history.

**Minimal fix**

Change to “existing durable practitioner-facing decision mechanism.”

### HR-13 — “Independent executor” contradicts the main definition of independence

**Severity:** Significant  
**Categories:** contradiction; unnecessary ceremony

**Exact sentences**

> “clean regeneration with status and checks captured outside the modified component as independent proof” — `SKILL.md:73`

> “Have an independent executor start from the retained revision…” — `references/evidence-tests.md:11`

**Loophole**

The main rule locates independence in the start state and external capture; the reference requires another executor. The latter can impose an unnecessary person or system.

**Minimal fix**

Replace the reference sentence with:

> Have an executor start from the retained revision and declared environment. Independence comes from the declared clean start and status/check capture outside the modified component; record the executor identity.

### HR-14 — Every new or changed check requires another practitioner

**Severity:** Significant  
**Categories:** net complexity; small-task burden

**Exact sentence**

> “A check created or weakened with the implementation cannot independently validate that behavior until a practitioner who did not author it reviews the criterion…” — `SKILL.md:77`

**Loophole**

For a small fix, a new regression check is normally written with the implementation. The clause makes another practitioner a universal execution step even when independent proof is not required.

**Minimal fix**

Preserve the evidence distinction without universal review:

> A check created or weakened with the implementation is supporting evidence, not independent proof. Require independent review only when the external-impact condition is true or the final claim explicitly asserts independent validation.

### HR-15 — Evidence tests are loaded after risky criteria should already be fixed

**Severity:** Significant

**Exact sentence**

> “Read references/evidence-tests.md before accepting a retained deliverable or claiming production execution verified.” — `SKILL.md:116`

**Loophole**

Recovery, repetition-safety, and equivalence conditions may need to be defined before the first retained run. Loading the reference only at acceptance is too late.

**Minimal fix**

Add:

> Also read it before the first retained execution when interruption, repetition hazard, nondeterminism, or external impact is true.

### HR-16 — Repetition safety is delayed until “scale”

**Severity:** Significant  
**Categories:** sequencing; external effects

**Exact sentence**

> “define and test idempotence or recovery **before scale**” — `SKILL.md:94`

**Loophole**

A single retained execution may already duplicate, overwrite, publish, or mutate external state. There may be no scale-up phase.

**Minimal fix**

Replace “before scale” with “before the first retained execution capable of the repeated effect.”

### HR-17 — The interruption threshold can be sandbagged

**Severity:** Significant  
**Categories:** softening; proportionality abuse

**Exact sentence**

> “if interruption would repeat more work than the bounded verification workload…” — `SKILL.md:93`

**Loophole**

The agent can choose an unnecessarily large bounded workload and make recovery appear unnecessary.

**Minimal fix**

### HR-18 — Human-curated primary inputs have no valid path

**Severity:** Significant  
**Categories:** legitimate practice blocked; adoption ambiguity

**Exact sentence**

> “Preserve stable origin… for acquired inputs; preserve complete lineage for generated inputs.” — `SKILL.md:69`

**Loophole**

Human curation is neither ordinary acquisition nor mechanical generation. The agent may force artificial automation or treat curation as an undocumented hand-produced intermediate.

**Minimal fix**

### HR-19 — Operational rules are not classified

**Severity:** Significant  
**Categories:** missing rule classification; false assurance

**Exact sentence**

> “Call evidence or history structural only when…” — `SKILL.md:79`

**Loophole**

The skill gives one classification criterion but no visible classification of its own rules and no short honor list. Readers cannot tell which guarantees depend on agent truthfulness.

**Minimal fix**

Add a compact classification block in `SKILL.md`, not a new file:

- structural only when an external control is confirmed;
- verifiable: revision match, native record provenance, output existence, criterion result, and claim-to-evidence link;
- honor plus review: complete load-bearing dependency identification, experimental influence disclosure, risk-condition answers, minimality, and human-native judgment.

### HR-20 — The universal core is long and repeats its references

**Severity:** Significant  
**Categories:** agent-process complexity; skill minimality

**Exact material**

`SKILL.md` is 126 lines and 2,116 words and is loaded before every state observation. The durable-path, evidence, record, and finish clauses repeat details also present in `cheats-and-countermeasures.md` and `evidence-tests.md`.

**Loophole**

The skill reduces project complexity while increasing the agent’s operating complexity on every trivial command. Repetition also creates drift risk.

**Minimal fix**

Keep the controlling priority, seven-step sequence, adoption rule, six risk conditions, completion rule, and reference-routing conditions in the core. Remove duplicated field lists and evidence explanations from either the core or references, never both. This is a clause consolidation, not a replacement skill.

## Human-native and technology observations

### Defects

- `SKILL.md:61` can create a wrapper merely to manufacture one operation. See HR-10.
- `SKILL.md:77` can add a reviewer to every new regression test. See HR-14.
- `SKILL.md:124` imposes a four-axis report on every project change. See HR-23.
- `SKILL.md:3` names current technologies in universal trigger metadata. See HR-24.
- The 2,116-word core is loaded before every state observation and repeats reference material. See HR-20.

### Deliberate tensions, not defects to remove

- The `Δ` presence mark adds chat telemetry but no project artifact or operating dependency.
- Thin wrappers constrain only an already-needed wrapper; their presence is not mandated.
- Experiments remain free and unrecorded, including dirty-tree work. The audit fixes adoption and real-production intervention ambiguity rather than imposing isolation or cleanup.
- State-carrying artifacts are permitted when executed cleanly in declared order; the rule is format-neutral.
- Risk archetypes remain illustrations and explicitly do not select requirements.

### Templates

The package contains no `assets/` directory and therefore no templates to test. This minimizes package complexity but differs from the earlier fixed design that retained four optional templates. Adding them is not recommended unless an actual consumer needs them; their absence creates no operating defect in `human-runner`.

### Interface metadata

`agents/openai.yaml` is compact and aligned with the skill’s objective. `allow_implicit_invocation: true` is consistent with the repository-level requirement to apply the skill before execution. No human-native defect was found there.

## Rule-classification audit

The current package does not classify its rules individually. The correct compact classification is:

| Rule group | Default class | What can verify or enforce it |
|---|---|---|
| Higher-priority authority, safety, and platform boundaries | Structural only where external access controls enforce them; otherwise honor | System controls, approvals, platform authorization |
| Presence mark | Verifiable in visible messages; not compliance evidence | Message inspection |
| Existing-path inspection and direct execution | Verifiable for visible operations; honor for completeness | Command/effect trace, project inspection |
| Production-path boundary completeness | Honor plus verifiable regeneration | Independent clean regeneration can reveal omissions but cannot prove every private influence |
| Experimental influence and decision disclosure | Honor | External traces and contemporaneous entries reduce but cannot eliminate the honor surface |
| Adoption and regenerated-output identity | Verifiable when revision match is fixed | Production evidence, output identity, clean regeneration |
| Revision immutability | Reviewable policy by default; structural only under external protection | Version history and confirmed external controls |
| Human-native form, minimality, and “practitioner would accept” | Honor plus human review | Named practitioner or user review and final diff |
| Durable-path artifact presence | Verifiable; completeness partly honor | Project inspection and clean regeneration |
| Environment and input identity | Verifiable for declared facts; completeness honor | Fresh build/validation, input acquisition, regeneration |
| Execution-record provenance | Verifiable; structural only with external capture and retention | Native platform record and external control |
| Claim-to-evidence mapping | Verifiable linkage plus honor for relevance | Claim audit and reviewer judgment |
| Completion/output existence | Verifiable | Canonical output and predeclared criterion |
| Diagnosis/intervention disclosure | Verifiable when platform evidence exists; otherwise honor | Authorization and native event record |
| Root-cause claim | Verifiable behavior plus honor for causal interpretation | Fail-before/pass-after and reproduction equivalence |
| Six risk-condition answers | Honor plus review of factual premises | Project context and named reviewer |
| Recovery, repetition, nondeterminism, and live-state checks | Verifiable when safely executed | Native results and timestamped observation |
| Handoff usefulness | Honor unless an actual practitioner tests it | Practitioner review |
| Complexity gate application | Honor plus diff review | Named practitioner/user review |

No rule is unconditionally structural merely because it appears in this skill.

## What could make practitioners ignore the skill

1. The 2,116-word core is loaded and cognitively applied before every filesystem or state operation.
2. Authored code or documentation can be mistaken for a derived output requiring production regeneration.
3. Only simple read-only commands have an explicit implicit fast path.
4. Every new regression test appears to require another practitioner before the behavior can be called verified.
5. The complexity gate runs twice around every applicable test.
6. Every project change asks for four net-complexity metrics.
7. A legitimate multi-command path can be collapsed into an unnecessary wrapper by the word “one.”
8. Risky evidence tests do not explicitly require a safe authorized representative state.
9. The detailed evidence reference is loaded too late for pre-run recovery and repetition decisions.
10. Blocked and complete status are joined by `or`.

## Accepted strengths

- The front of the skill unambiguously makes minimal complexity controlling.
- The agent may test dirty, experiment freely, and discard failures without a diary.
- Adoption includes copied, retyped, paraphrased, converted, moved, summarized, and fixed values.
- The skill explicitly rejects universal artifact bundles and custom assurance machinery.
- Evidence is native, claims are scoped, and lack of evidence narrows the claim rather than creating a framework.
- The six risk conditions replace domain-based tiers.
- Existing runbooks, decision mechanisms, and handoffs are preferred and new ones are conditional.
- Current status requires a live timestamped observation.
- The skill tells the agent to stop redundant checking.
